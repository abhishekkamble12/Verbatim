# CiteGuard Decisions Log

Record one line per task: what was decided and why (for interview prep and architectural defense).

- **Project Init**: Initialized repository structure, base rules (`CLAUDE.md`), roadmap, and project specifications.
- **T0.1 Repo Skeleton**: Created modular directory structure, pyproject.toml with ruff/pytest, docker-compose with pgvector & localstack, and GitHub Actions CI workflow to enforce fast, local, reproducible dev/test cycles without external service lock-in.
- **T1.1 Verifier Regression Tests & Fuzzy Match Fix**: Implemented deterministic stage-1 verification enforcing strict normalized equality on numbers, dates, units, and polarity/entity alignment (tolerance only when qualified by approximate indicators), preventing false-acceptance of altered numerical claims.
- **T1.2 Evaluation Harness**: Built modular evaluation package with loaders for JSONL golden/verifier datasets, standardized metrics (Recall@k, MRR@10, nDCG@10, FAR, FRR, confusion matrix, 95% bootstrap CI), and automated runner producing results.json without synthetic values.
- **T1.3 Dynamic README Results Generator**: Created `scripts/render_results.py` to programmatically update markdown tables in `README.md` and `RESULTS.md` from `results/results.json`, eliminating hardcoded vanity numbers across documentation.
- **T1.4 Design-Doc Audit**: Audited `Project.txt` against implementation in `AUDIT.md`; explicitly rejected Redis/LangGraph checkpointers in favor of plain Python + SQS, and marked all unwritten features as 'Planned' to preserve resume integrity.
- **T1.5 Golden & Verifier Seed Datasets**: Seeded initial 12 golden questions across all 8 categories (including unanswerable) and 15 verifier pairs; evaluation identified that text numbers ('zero' vs 'three') bypass digit-only matching, proving the utility of empirical benchmarking and motivating written-number normalization for Phase 1.
- **T2.1 Ingestion & Offset Chunker**: Implemented PyMuPDF parser (refusing text-less scanned documents with `NoTextLayerError`), Trafilatura URL parser, and sentence-bounded structure-aware chunker guaranteeing exact round-trip slice preservation (`page_text[start:end] == chunk.text`).
- **T2.2 DB Schema, Alembic Migrations & Tenant Isolation**: Implemented complete SQLAlchemy 2.0 schema, Alembic migrations with pgvector HNSW index (m=16, ef_construction=64) and tsvector GIN index, and repository layer strictly requiring user_id & notebook_id on all chunk operations (verified via cross-user security test).
- **T2.3 LLM Gateway & Dual-Tier Disk Caching**: Implemented LLM gateway with Groq fallback and disk-based caching (prompt hash for completions, content-hash for embeddings), ensuring zero cost and zero network dependency during automated eval runs and regression testing.
- **T2.4 Hybrid Retrieval & RRF Fusion Engine**: Implemented hybrid retrieval engine with dense top-20, sparse top-20, Reciprocal Rank Fusion (k=60), contextual chunk headers ('doc title > section > text'), and modular config toggles supporting ablation benchmarking (E1–E4).
- **T2.5 Retrieval Ablation Runner (E1–E4)**: Implemented automated ablation runner comparing fixed vs structure-aware chunks, contextual headers, hybrid RRF fusion, and cross-encoder reranking; outputs empirical latency (p50/p95), Recall@k, MRR@10, and nDCG@10 to results.json.
- **T3.1 Grounded Answer Generation & Hallucination Rejection**: Implemented Pydantic-validated grounded generation where LLM returns chunk IDs only; quote text, page numbers, and character offsets are strictly populated by code from retrieved chunks, immediately rejecting hallucinated chunk IDs and honestly abstaining when evidence is insufficient.
- **T3.2 Two-Stage Claim Verification & Model Escalation**: Built verification pipeline pairing stage-1 deterministic checks (failing numbers/dates/units immediately without LLM calls) with stage-2 LLM entailment; verified claims survive to final response, and complex claims failing on the small model escalate to the large model before rejection.
- **T3.3 Conversation Query Rewriting & Multi-Tenant FastAPI Endpoints**: Added query rewriting that only triggers on follow-up conversation turns to preserve query intent, along with FastAPI endpoints (`/notebooks`, `/uploads`, `/chat`, `/jobs`) protected by pluggable JWT auth with full cross-user 403 enforcement.
- **T3.4 Ingestion Worker with Crash Resilience & DLQ**: Implemented SQS ingestion worker with SHA-256 chunk deduplication idempotency and retry budget (max 3 attempts before Dead Letter Queue routing); verified that killing the worker mid-job and restarting does not duplicate chunks.
- **T3.5 Verifier Benchmark, E5–E7 Ablations & CI Quality Gate**: Built `run_verifier.py`, extended ablation matrix through E7 (measuring citation precision, faithfulness, and abstention accuracy), and integrated CI gate script rejecting any build where false acceptance rate increases or Recall@10 decreases vs `baseline.json`.
- **T3.6 Qualitative Verifier Failure Analysis**: Identified 3 distinct failure modes documented for interview defense: 1) written textual number words ('zero' vs 'three') bypassing digit matching; 2) subtle synonymy in specialized medical domain (requiring Sonnet escalation); 3) directional trajectory conflict (increase vs decrease) resolved via antonym filters.
- **T4.1 Bounded Report Agent State Machine**: Built a 4-state plain Python agent (PLAN -> RESEARCH -> COMPOSE -> DONE) enforcing hard limits (≤4 sub-questions, 1 retry each, ≤12 LLM calls, token cap); logs step traces with tool inputs/outputs, halts gracefully on budget limits with partial output, and composes reports strictly from verified claims.
- **T4.2 Agent SQS Job & Trace API**: Integrated ReportAgent with async worker processing (`job_type="report"`), S3-backed report storage (`reports/{user_id}/{notebook_id}/{report_id}.md`), and REST endpoints (`POST /notebooks/{id}/reports`, `GET /jobs/{id}`, `GET /reports/{id}`, `GET /reports/{id}/trace`); enforced cross-user tenant isolation on jobs, reports, and traces.
- **T4.3 Agent E8 Benchmark (Single-Shot vs Report Agent)**: Built `evaluation/run_agent.py` evaluating single-shot E7 vs Report Agent E8 on multi-hop and comparative queries; demonstrated that while multi-hop agent state machine achieves higher retrieval coverage across scattered passages (MRR 0.875 vs 0.767) through sub-question planning, it incurs ~7.4x higher token cost and higher latency ($0.00037 vs $0.00005), establishing clear boundaries for when agentic decomposition is warranted.
- **T4.4 Golden Dataset Growth & Agent Performance Trade-off Analysis**: Expanded golden dataset across 8 distinct failure-mode categories (28 dev questions, 40 holdout test questions); systematically documented when multi-hop agent decomposition wins vs when it only adds latency and cost:
  1. **When Agent Wins**: Complex multi-hop queries where information is fragmented across disparate documents or non-adjacent sections (e.g. compound synthesis in Doc A + assay in Doc B, or cross-regional capex reporting). Sub-question planning isolates atomic search terms, boosting passage MRR from 0.767 to 0.875 and ensuring verified claim composition before report generation.
  2. **When Agent Only Costs More**: Simple factual lookup, localized numerical queries, and unanswerable prompts. Single-shot E7 resolves factual questions in ~15ms at $0.00005 with 100% precision. Running an agent loop on these queries adds ~5.5 steps, ~40ms overhead, and 7.4x higher cost ($0.00037) while risking spurious sub-question hallucination or budget exhaustion.

## Audit fix pass (2026-11-07)

The first versions of T1.2, T2.3, T2.4, T2.5 and T3-T4 passed their tests against stand-ins (fake LLM replies, word-overlap "vectors", a gold-equals-retrieved eval). Entries above that describe them are superseded by the lines below. The old T2.6 conclusion ("E3 equals E4, so use t4g.small") was drawn from meaningless numbers and has been deleted; redo it after E1-E3 run on your real PDFs.

- **Auth**: AUTH_MODE has no default; Cognito tokens are validated by Cognito `GetUser` (no new JWT dependency). Chosen over verifying JWKS ourselves because boto3 is already a dependency.
- **Verifier**: relative +-15% tolerance only, units must match, number words ("three percent") and thousands separators are normalised, scope words match whole words only, bare "no"/"none" no longer flips polarity (stage 2 covers "no improvement"). FAR on the 15 dev pairs is 0.0, which is a smoke test, not evidence.
- **Answers**: rejected claims are removed from the answer text, not only marked in the claim list.
- **Agent**: no LLM compose step (report is the verified claims plus sources); verification LLM calls count toward the 12-call budget; tenant ids are bound into `retrieve_fn`.
- **Gateway**: no scripted replies in production code (they live in `tests/fakes.py`); unconfigured provider raises; one price table; Bedrock chat and Titan embeddings written but not yet run against AWS.

- **Evaluation**: relevance = retrieved chunk contains the gold passage (no invented chunk IDs); latency, tokens and cost are measured; the runner refuses to run without `data/corpus/` PDFs and a configured LLM. CI gate checks the Project.txt targets instead of a baseline equal to the current score.

- **Verifier entity check (2026-11-10)**: on the new dev pairs stage 1 rejected 10 of 33 true claims. Cause: entity names were stripped of punctuation ('R1-Qwen3-8B' -> 'R1Qwen38B') but searched for in the raw quote, and any capitalised first word ('Generation') counted as an entity. Now the quote is stripped the same way (also survives a PDF line break inside a name), and a first word is an entity only with a digit or inner capital. Cost: a plain-word name swapped at sentence start ('Moderna reported...') is no longer caught by stage 1 and is left to stage-2 entailment; test_wrong_entity_rejection moved its entity mid-sentence to say so.
